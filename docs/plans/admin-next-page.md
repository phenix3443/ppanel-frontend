## 用户、任务与选择理由

目标用户是已有后台访问权限、需要辨认工单状态并进入既有处理流程的管理员。能力水平、使用设备分布与使用频率 UNKNOWN；“管理员能看清状态并选对行操作”是本轮待验证的设计目标。

关键流程：Home 工单卡或现有侧栏 → 工单列表 → 选择现有状态并点筛选 → 阅读标题、用户、状态、更新时间 → 点回复或查看打开既有抽屉 → 关闭抽屉继续列表。关闭工单仍必须经过现有确认。本轮不改抽屉设计与业务行为。

| 候选 | 当前可读证据 | 取舍 |
|---|---|---|
| 工单列表 | 四个业务列、一种状态筛选；Home 已有直接入口；回复/关闭/查看已存在。见 [ticket/index.tsx](../../apps/admin/src/sections/ticket/index.tsx)、[Home KPI](../../apps/admin/src/sections/dashboard/components/kpi-grid.tsx) | 推荐：可限定在列表呈现，验收边界明确 |
| 服务器页 | 除列表外还有动态倍率、服务器配置、协议/资源指标、在线用户详情、节点配置、编辑/安装/复制/删除/拖动排序。见 [servers/index.tsx](../../apps/admin/src/sections/servers/index.tsx) | 本轮不选：要保留并验证的区域和写入入口更多；这不代表服务器需求价值较低 |

已知产品问题是 Home 视觉已确认、其他页尚未延续该体系；“工单更常用”“现有列表让用户漏单”“手机处理更快”都没有用户证据。本轮选择依据是入口连续性和范围复杂度，不是需求热度。CEO 决定业务优先级，CTO 决定后续技术方案与工程安排。

## 列表状态与动作

这些是下一次实施时的呈现验收要求，不声称当前应用已满足。本轮 SVG 只表达各状态的结构。

| 状态 | 应见内容 | 动作与判定 |
|---|---|---|
| 正常 | 页面标题、现有工具栏、状态筛选、四业务列/手机条目、行操作、真实分页 | 全部状态默认不筛选；status=4 仅查看，其他状态沿用回复/关闭；关闭保留确认 |
| 首次加载 | “正在加载工单…”或稳定占位，保留页头与筛选位置 | 不出现“0 条”“暂无工单”，没有可点击的旧行操作；刷新请求进行时禁用重复刷新 |
| 刷新/筛选/翻页加载 | 保留当前已应用条件，说明“正在加载工单…”；结果区暂不开放旧行操作 | 新选择尚未点筛选时显示既有“未应用修改”；加载完才替换结果；不增加自动轮询 |
| 首次失败 | “工单加载失败，无法确认当前结果，请重试”与重试按钮 | 失败优先于空状态，不显示成功的 0；重试沿用同一次查询参数 |
| 有旧结果后失败 | 同一失败说明，旧结果如保留须标“上次结果，未更新”；旧结果行操作不可用 | 不把上一页或上一筛选结果显示为当前成功；不添加本地编辑或补偿业务 |
| 成功且全部状态为空 | “暂无工单”；没有新增工单按钮 | 仅成功的有效空响应可显示；不出现 0/1 页或 NaN |
| 成功且筛选结果为空 | “没有符合条件的工单”，提供已有清除筛选动作 | 清除条件并回第一页，不改后端、不添加搜索 |
| 401/403 | 沿用现有全局认证/权限处理；就地说明无法加载时不得写“暂无工单” | 不提供提权、切换账号或绕过入口；实际错误路径待实施取证 |

没有有效 `list/total` 的异常响应不能当作成功空列表。未来技术方案由 CTO 安排确认现有请求层如何识别；不以这项设计要求授权修改契约。

## 桌面与手机布局

线框均为黑白结构图，**不是新增的黑白视觉主题**。正常、加载、失败、全部为空、筛选为空五种状态各有桌面和手机版本，见 [wireframes 目录](admin-ticket/wireframes)。正常图内的数据为合成示例，非真实用户数据。

- 桌面结构画布 1280×800：现有侧栏与顶栏 → 标题/工具栏 → 状态筛选 → 四业务列表格与行操作 → 分页。标题列占余量，用户/状态/时间/操作保持可读。实际应用验收用 1440×900；线框不承诺精确像素复刻。
- 手机结构画布 384×960（加长展示滚动后的分页），应用验收用 390×844。现有导航收进原侧栏入口；工具栏与筛选分行；同一列表行改为上下排布的条目，标题 → 状态 → 用户/更新时间 → 原行操作。手机和桌面共用同一页数据、字段与动作，不生成第二份数据或增加新路径。
- 长标题可换行，用户标识与时间不可挤出屏幕；若截断，键盘聚焦和触摸打开现有详情均能读完整标题，不能只依赖 `title` hover。异常长的无空格内容也必须断行。
- 手机触控目标至少 44×44 CSS px；工具栏可换行，分页保留页码和 10/20/50/100 选择。线框省略每页数量菜单的展开态；实现不得因此删除该功能。
- 列显示/重置继续可用，两种布局尊重相同的列可见性；操作列不可隐藏。手机初始展示全部四业务字段，不能仅为省空间隐藏用户和更新时间。
- 页面、内层滚动容器、列表条目都不得发生横向溢出；不能靠裁剪隐藏无法触达的动作。390×844 不要求全部工单或分页在首屏，用户可纵向滚动。

线框区域说明：**1** 现有导航；**2** 刷新、列显示、重置；**3** 状态筛选与应用/清除；**4** 结果或状态反馈；**5** 分页（仅有有效结果时）。

## 引用 A 的视觉体系

依据 [admin.css](../../apps/admin/src/styles/admin.css)，未来实现复用 A 的暖黑/暖白三层底色、细边框、圆角与 IBM Plex 字体；数字采用 `tabular-nums`。深色 canvas/surface/raised 为 `#151412` / `#25221e` / `#2d2924`，浅色为 `#f1f0ed` / `#fcfbf8` / `#f7f6f3`。

橙色 `--ds-signal` 表示选中与主操作，`--ds-warning` 用于待跟进状态；待回复使用 info、已解决使用 success、已关闭使用中性色并保留文字。关闭按钮使用 danger。状态不能仅靠颜色或持续闪烁区分；不恢复整体健康徽标。深浅主题的正文和状态文字对比度目标均 ≥4.5:1。

**当前 token 映射只作用于 Home，并未自动覆盖工单。** 本建议要求后续只在本页及其必要入口范围延续视觉，不授权改全局共享 token、其他 admin 页或 user；具体作用域和复用方式由技术方案确定。抽屉、UserDetail、关闭确认维持原组件行为，本轮不做其视觉重构。

## 设计检视与明确风险

按 design-critique 对本稿检视，用户任务上下文是上文的管理员与列表选择流程，属于待验证假设。

**必须处理（未来本页实施验收前）**

- 状态表达：共享表格首载失败时可能同时留下通用空行；本稿规定失败优先，避免“加载失败但看起来没工单”。依据 `pro-table.tsx:358` 与 `:470`，是源码风险而非已观察到的用户错误。
- 手机与可达性：不可只缩小桌面表格；保留四业务字段和原操作，触控目标至少 44px。必须实测长标题、内层溢出、焦点和列显示，当前线框不足以证明这些交互。

**应处理（不扩大本轮实现授权）**

- 词义一致性：沿用 1/2 的既有名称，不把“待回复”写成管理员待办；不能从单页内排序推导全局队列顺序。
- 抽屉风险记录：`ticket/index.tsx:46` 只取 data/refetch，`:281` 的 `ticket?.status !== 4` 在未加载时也成立；加载失败时回复区可能出现。尚未浏览器确认。本次列表建议不改抽屉，未来工程派单前由 CTO 明确是否单列同页状态修复，不能假装本稿已修复或擅自扩展。

**可后置**

- 持续状态闪动的必要性待验证；视觉延续建议用静态状态标识，不增加消息通知。URL 同步筛选、跨页全局排序均不在本次最小范围，不因界面指南建议而加进来。

**保留的优点**

- Home 与侧栏已有入口；四业务列和单状态筛选便于限定范围。
- 共享表格已有显式应用/清除、刷新、错误重试；关闭已有确认，应延续。
